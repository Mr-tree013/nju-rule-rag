# NJU Rule RAG — 技术报告

> 南京大学本科生校规智能问答系统 · V0.6.4 · 2026年6月

## 1. 项目概述

NJU Rule RAG 是一个面向南京大学本科生的校规智能问答系统。学生用自然语言提问（如"补考没过怎么办""缓考怎么申请"），系统从 147 份校规文档中检索相关内容，由大语言模型生成带来源引用的答案，并根据置信度自动分级（自信回答 / 谨慎回答 / 转人工）。

**核心指标：**

| 指标 | 数值 | 说明 |
|------|------|------|
| 文档覆盖 | 147 份 → 3286 个片段 | 含教务处正式文件、学生手册、官方FAQ |
| 评测题量 | 144 题 | 覆盖选课、缓考、补考、重修、绩点等 20+ 主题 |
| 忠实度 (Faithfulness) | **3.30/5** | 双 judge 平均（DeepSeek + Qwen3） |
| 相关性 (Relevance) | **3.80/5** | 答案是否切题 |
| 平均延迟 | **1.76 秒** | 从 5.03 秒优化而来（-65%） |
| 关键词命中率 | 77.8% | 答案是否包含预期关键词 |
| 端到端成功率 | 144/144 (100%) | 零崩溃、零错误 |

## 2. 系统架构

```
学生提问 → 风险分类 → 主题路由 → 混合检索 → 交叉编码器重排 → LLM生成 → 事实核验 → 格式化输出
```

### 2.1 检索管线

- **混合检索引擎**：BM25（关键词）+ BGE-M3 稠密向量（语义）+ 优先级加权，权重经网格搜索调优（0.25 / 0.45 / 0.30）
- **两阶段重排**：粗筛 20 候选 → BGE-Reranker-v2-m3 交叉编码器精排至 12，分数融合采用 Sigmoid 校准
- **置信度分级**：基于 top-1 分数和 top-3 均值，自动决策三级响应策略
- **主题软路由**：识别 20+ 校规主题，对相关来源文档 1.2× 分数加权

### 2.2 生成管线

- **基座模型**：Qwen3-8B（4-bit 量化，Ollama 部署），温度 0.35
- **思考模式抑制**：通过 `/no_think` 指令 + 空 `<think>` 块注入消除推理阶段 token 消耗
- **提示词工程**：经 6 轮迭代，包含强资料绑定指令、负面示例、200 字约束
- **回退机制**：高风险问题自动路由至 DeepSeek，LLM 故障时 3 次重试

### 2.3 后处理护栏

- **NER 事实核验**：提取答案中的数字、日期、URL、金额，与检索到的资料片段逐条比对
- **三级惩罚机制**：硬删除（零容忍项不匹配）→ 语言对冲（部分匹配）→ 降级为转人工（3+ 项失败）
- **引文验证**：答案句与来源片段的 bigram 重叠度检测
- **长度控制**：600 字截断，高风险问题自动追加联系方式模板

### 2.4 工程优化

- **API 层替换**：从 Ollama 的 OpenAI 兼容端点（`/v1/chat/completions`，~2.7 秒额外开销）切换到原生端点（`/api/generate`，直通 CUDA），延迟 5.03s → 1.76s（-65%）
- **查询缓存**：内存 LRU（1 小时 TTL）+ 持久化 chunk 签名缓存（7 天 TTL），chunk ID 变化自动失效
- **SSE 流式输出**：三阶段推送（检索完成 → token 级生成 → 事实核验修正），感知延迟降至 0.5 秒
- **空响应容错**：生成空内容时自动以 0.3 温度重试

## 3. 技术亮点

### 3.1 延迟优化的意外发现

常规认知是"模型推理慢"→ 换硬件或量化。但实测发现，Ollama 的 OpenAI 兼容层对每次请求额外消耗约 2.7 秒（重复 tokenize + JSON 构建 + 响应翻译），而原生 `/api/generate` 端点仅需 ~1.0 秒。只需修改 HTTP 调用即可获得近 3 倍加速——一行基础设施没改，一个模型没换。

### 3.2 评测系统的自我校准

建立了双 judge 评测体系（DeepSeek + Qwen3 本地模型），并通过 25 题人工抽检计算 Spearman 相关性，发现：

- DeepSeek judge 在忠实度维度与人类评分的相关系数仅 r=0.26（几乎随机）
- 人类认为"正确拒答"（"资料里没写，建议问教务员"）的答案，judge 系统性判为低分
- 揭示了 LLM-as-judge 的结构性局限：judge 看不到原始资料，无法区分"忠实拒答"与"编造答案"

### 3.3 检索质量的系统诊断

通过 F2（模型编造/忽视检索）失败案例的逐题分析，发现：

- 21/31 的 F2 案例实为检索失败（正确文档未进入 top-5）
- 根因不是缺文档（45 个 gold 文档全部已入库），而是三个检索质量问题：
  - 5 份大杂烩文档（规章制度汇编）共 2,100+ 片段垄断排名
  - 一份缓考核心文档（nju-jw-004）的文件从磁盘丢失
  - 26 份 gold 文档因单片段导致 BM25 权重过低
- 针对性修复后，5/5 测试题 gold 文档进入 top-5

### 3.4 提示词迭代的系统方法

经 6 轮提示词迭代，建立了一套 RAG 系统提示词设计原则：

| 版本 | 关键变化 | F 变化 |
|------|---------|--------|
| v1-v3 | 初始版本，含详细少样本示例 | ~2.3 |
| v4 | 路线 B：精简 + fact_check 上线 | 2.94 |
| v5 | 强资料绑定 + 去除防御性语言 | 3.28 |
| v6 | 恢复负面示例 + 核心原则 | 3.10→3.30 |

核心经验：负面示例（"答得不好（避免）：编造数字、用常识补充"）比正面示例更能抑制模型编造行为。

## 5. 技术栈

| 层级 | 技术选型 |
|------|---------|
| 大语言模型 | Qwen3-8B（Ollama Q4_K_M 量化，/api/generate 原生端点） |
| 回退模型 | DeepSeek-Chat（高风险 + 故障转移） |
| 嵌入模型 | BGE-M3（sentence-transformers，1024 维稠密向量） |
| 重排序 | BGE-Reranker-v2-m3（交叉编码器） |
| 关键词检索 | BM25（jieba 分词） |
| 向量存储 | ChromaDB |
| Web 框架 | FastAPI（SSE 流式 + REST） |
| 评测 | DeepSeek + Qwen3 双 judge + 人工抽检校准 |
| 部署 | WSL2 Ubuntu + GPU-PV，Windows 原生可选 |
| GPU | NVIDIA RTX 4070 Ti Super 16GB |

## 6. 待完善方向

- **LoRA 微调**：当前模型在 31 个编造类问题上仍有提升空间，需积累 500+ 条真实反馈数据后训练 LoRA-v3
- **评测可信度**：LLM-as-judge 在忠实度维度与人类评分相关性不足，需增加带来源文档上下文的 judge 或引入更多人工校准
- **反馈飞轮**：已建设 `/feedback` 端点 + 导出脚本，等待线上流量积累训练数据
